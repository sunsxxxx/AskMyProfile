# 智能仓储协同平台

## 项目背景

面向连锁零售企业的仓储协同平台，负责采购入库、门店调拨、库存盘点和库存预警。项目周期为 2024 年 3 月至 2024 年 11 月，核心目标是减少高并发调拨时的超卖和库存不一致。

## 我的职责

我负责库存中心和调拨单模块的后端设计与开发，包括库存扣减接口、Redis 缓存、RabbitMQ 异步事件、MySQL 表结构，以及相关监控告警。商品、采购和前端页面由其他成员负责。团队共 6 人，其中后端 3 人。

## 技术栈

Java 17、Spring Boot 3、MyBatis-Plus、MySQL 8、Redis 7、RabbitMQ、Docker、Prometheus、Grafana。

## 系统架构

系统按商品、库存、采购和调拨四个业务模块拆分，但部署形态仍是模块化单体。库存变更在本地事务提交后写入 outbox 表，再由后台任务投递 RabbitMQ；下游消费库存事件更新预警数据。没有为了“微服务”而拆分独立服务。

## Redis

Redis 用于热点 SKU 库存查询和调拨单幂等。库存详情使用 Cache Aside，key 为 `inventory:{warehouseId}:{skuId}`，TTL 为 10 分钟并附加 0 至 120 秒随机值。写操作以 MySQL 为准，事务提交后删除缓存；删除失败会进入重试队列。调拨请求以业务请求号作为幂等键，使用 `SET NX EX` 拦截短时间重复提交，数据库唯一索引作为最终兜底。

没有使用 Redis 分布式锁执行库存扣减，因为锁续期和故障恢复会增加复杂度。库存扣减通过 MySQL 条件更新 `available_stock >= quantity` 保证不出现负库存。

## MySQL

库存表以仓库 ID 和 SKU ID 建联合唯一索引。扣减语句将库存条件写进 `UPDATE`，根据受影响行数判断库存是否充足。库存流水单独落表，记录业务单号、变更前后数量和操作类型，便于审计与对账。

## RabbitMQ

库存事件可能重复投递，因此消费者先用事件 ID 查询消费记录；消费记录与业务更新放在同一数据库事务中。失败消息按 10 秒、1 分钟、10 分钟分级重试，超过次数后进入死信队列并触发告警。

## 遇到的问题

压测时出现库存接口偶发读取旧值。证据是 MySQL 已完成扣减，但删除缓存的任务在一次 Redis 网络抖动中失败，后续请求继续命中旧缓存。

## 解决方案

我把缓存删除操作改成事务提交后的事件处理，并为失败事件写入本地重试表；重试任务按指数退避执行，同时用指标记录待重试数量。数据库始终是最终事实源，缓存仅影响短时展示，不参与是否允许扣减的判断。

## 性能优化

压测环境为 4 核 8 GB 单实例、10 万个 SKU 热点分布。库存查询接口在 300 QPS 下的 P95 从 180 ms 降至 42 ms，缓存命中率约 91%。这些数据仅代表测试环境，不等同于生产数据；生产峰值 QPS 未记录。

## 项目亮点

通过条件更新、唯一索引和消费幂等形成多层一致性保护；为缓存删除失败设计了可观测、可重试的补偿链路，而不是把 Redis 当作唯一事实源。

## 可以改进的地方

如果继续迭代，我会把 outbox 轮询改为 CDC 方案，并补充库存流水的自动对账任务。目前没有做跨机房容灾。
